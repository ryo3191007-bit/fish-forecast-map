## 1. 現在の結論

FishTraceは、福岡県糸島市西岸から唐津湾、伊万里湾、平戸方面までを対象に、釣り場を探す・現地調査する・釣果を記録する・共有するための個人開発Webアプリです。地図・地点情報・客観的な環境情報・本人釣果を一つの導線で確認します。

2026-07-28時点では、アプリ基盤・地点master・52地点の再調査・座標監査・地点詳細UI・本人実地調査・本人釣果・認証基盤は大きく整備済みです。現在の主作業は、魚種生態調査v2をSchema v1.4.0へ統一する最終2Batchです。

- 国土地理院の淡色地図。
- GEBCO_2026 15秒を第一source、ETOPO 2022 60秒をfallbackとする参考水深・3D地形。
- Open-Meteo Weather / Marineによる7日間の環境予報。
- 気象庁防災情報XMLを利用したfail-closedの警報・注意報安全ゲート。
- 地点master 52件。広域地点監査後、通常の新規選択・地図・地点情報へ出す行き先は47件。
- 全52地点の地形・構造・足場・設備・規制等の再調査完了。
- 全52地点の座標監査完了。Issue #294で2地点、Issue #296で残り50地点を監査し、必要地点だけ補正。
- 地点情報タブは `環境 / 釣場 / 地形 / 魚種`。
- 釣場・地形タブは全通常表示地点で項目構成を共通化し、未確定値を隠さず `未確定` と表示。
- 魚種タブで本人の登録釣果魚種、事前調査魚種、本人実地調査を分離表示。
- ログインユーザー本人が釣場・地形・魚種の実地調査情報を追加・編集・削除可能。調査済み値とは別の `user_contribution` として保持し、SCOREや安全情報を上書きしない。

- Supabase master read、Auth、owner-scoped read/write、localStorage fallback・明示移行。
- 認証はメールアドレス + パスワード方式。既存Magic Linkユーザーはpassword recovery経由で既存user idを維持して移行可能。

## 7. Supabase / Auth / DB

### 7.1 Auth

現在の通常ログインはメールアドレス + パスワードです。

- 新規登録: `signUp()`。
- ログイン: `signInWithPassword()`。
- パスワード設定・再設定: `resetPasswordForEmail()` + recovery flow。
- 既存Magic Linkユーザーのuser idを作り直さない。
- Google / social OAuthは現在使用しない。

詳細: `docs/AUTH_SETUP.md`

本番Custom SMTPはIssue #322で未対応です。コード実装済みと外部サービス設定済みを混同しません。

### 7.2 DB変更ルール

- `supabase/migrations/`を正本とする。
- forward-only。
- 既存地点ID、魚種ID、本人釣果を推測で破壊・再割当しない。
- repositoryへmigrationがmergeされたことと、remote DBへ適用済みであることを分離する。
- migration入りPRを`main`へmergeするとproduction workflowが起動するため、merge前に利用者へ明示する。
- remote適用完了はproduction statusを確認して判断する。
- 利用者の明示指示なしにremote DBを手動操作しない。

### 7.3 secret

GitHub、Issue、PR、チャット、ログへ次を貼りません。

- Supabase secret / service role key。
- DB password / connection string。
- `.env.local`。
- 実password。
- SMTP credential。
- 海しるAPIのサブスクリプションキー等の認証情報。

## 10. 最重要の作業ルール

1. 作業開始時にGitHub正本を再確認する。
2. 1タスク = 1 Issue = 1 PR。
3. `main`へ直接fileを作成・更新・削除しない。
4. 無関係な変更を混ぜない。
5. Codex起動は利用者の明示許可後。
6. Codexへ渡す要件・対象外・完了条件・test条件は最初の1回へ統合する。
7. 同じPRへ2回目のtop-level `@codex`指示を重ねない。
8. CI greenだけでmerge可能と判断しない。
9. PRのmergeは利用者の明示判断後。
10. Issue closeはmerge確認後、利用者の明示指示に従う。
11. migration入りPRはremote DB自動適用の可能性をmerge前に説明する。
12. remote DBを無断で手動操作しない。
13. 不明な値をAI推測でconfirmedにしない。
14. placeholder URL・架空sourceを正式根拠にしない。
15. 未承認binaryを作成・保存・変更・commitしない。
16. 実施していないbrowser確認、外部送信、DB反映を完了扱いしない。
